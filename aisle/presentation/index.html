Navigation for blind and low-vision people that doesn't stop at the front door.

No beacons.

No store partnership.

No extra hardware.

One phone.

Aisle Be There is not a chatbot and not a smart-glasses demo. It is one iOS app that a blind person can run today on the phone they already own. Everything in this deck is built, running, and field-tested in a real grocery store. Four of us, one weekend.

The gap

Maps gets you to the address. Then it goes quiet.

Aisle Be There covers the last hundred metres and the last arm's length.

The last mile is solved. The last hundred metres and the last arm's length are not. Inside a store there is no map at all, describer apps narrate instead of guiding — "a refrigerator section with several doors" does not tell you which way to walk — and asking a stranger costs the independence that was the point of the errand. That is the whole gap we went after.

One errand, three handoffs

01

Walk there

Route geometry and haptic nudges.

02

Find the aisle

The camera reads signs and shelves.

03

Reach for it

Hand tracking closes the last foot.

Each handoff is automatic. The user never picks a mode.

Most assistive tools do exactly one of these three. The hard engineering is the seam between them — knowing you have entered the store, knowing you have reached the right shelf, knowing to switch from walking cues to hand cues. Under it sit three tiers: on-device ARKit, CoreML and Vision OCR every frame for anything a haptic depends on; Claude on occasional still frames for the hard visual questions; and Nemotron as the decision layer. Street and store video never leaves the phone.

The design rule everything else follows from

Silence is the reward.

On course, it says nothing. Twelve words maximum when it does. Six words are banned outright, and it never decides a crossing.

This is what separates us from a camera wired to an LLM. The banned list — safe, clear, go, cross now, no cars, you can cross — is a real linter in the repo: a build that would speak any of them fails. The twelve-word cap is checked at build time too. That constraint changed the architecture, because if you cannot say "go" you have to be genuinely useful with position and haptics instead. Four haptic patterns carry most of it: COURSE, TURN, STOP, CONFIRM.

Beyond the Chatbot

Nemotron never talks to the user.

It is the decision layer behind the app: JSON in, JSON out, executed by code rather than read aloud. Six jobs.

parseIntent routeCompile taskPlan disambiguate crossingAnnounce answer

nvidia/nemotron-3.5-lightning-30b-a3b  ·  it never sees an image

The track slide. Nemotron is not the thing the user talks to — its output is parsed, schema-validated and executed. If it returned prose the app would break, not degrade. It races a deterministic local template and the first valid answer wins, so a timeout is a slightly plainer cue, never an outage. Nothing time-critical waits on it. It also never touches a pixel: Claude is the one that sees images.

Two failures found in the NIM endpoint: guided_json returns HTTP 400, and streaming's first chunk takes ~34 s where the whole non-streamed answer takes ~1 s. Both are dated in our source.

Full eval, confusion matrices and latency tables live in the repo.

Be honest about the headline: the deterministic template beat the live planner race on raw intent accuracy, 98.3 to 93.3 — which is exactly why the race exists. What Nemotron buys is the grounded multi-step task plan and the phrasings the template has no rule for. The NIM findings are the track's "failure you found": we measured them, dated them in a comment, and shipped non-streaming json_object mode with the schema in the prompt instead of discovering it in a store. The 10,313 records came from a grocery run that went wrong — context defaulting to home, and relative depth used as a hard veto on movement cues. Say plainly which of those are fixed in the build you just demoed.

What we hold ourselves to

The bar isn't “it described the shelf”. It's “you left with the bananas”.
